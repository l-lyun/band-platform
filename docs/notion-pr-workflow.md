# Notion PR Documentation Workflow

## 목적

BandMaster 작업은 GitHub Issue, Branch, Pull Request, Notion 작업 문서를 함께 남긴다.

PR마다 Notion 문서를 1개 작성해서 작업에 필요했던 개념을 학습 자료처럼 남긴다.

이 문서의 1차 목적은 구현 로그 보관이 아니라 사용자가 해당 PR의 핵심 개념을 다시 찾아보지 않고 학습할 수 있게 만드는 것이다.

변경 파일, 커밋 목록, 단순 구현사항 나열은 PR과 GitHub에서 이미 확인할 수 있으므로 Notion 문서의 중심에 두지 않는다. 필요할 때만 참고 정보로 짧게 남긴다.

## 기능별 문서 관리

메인 페이지에서는 기능별 페이지를 단순하게 분리한다.

현재는 다음 두 페이지를 기본으로 사용한다.

- 공통 기능: 공통 에러, 예외 처리, Spring Security, 인프라처럼 여러 기능에서 같이 쓰는 기반 작업
- 로그인 기능: 회원가입, ID/PW 로그인, 계정 잠금, 토큰 인증처럼 로그인 MVP에 직접 속한 작업

기능별 페이지 안에서는 이슈 목록을 먼저 보여준다.

- 이슈마다 GitHub Issue 링크를 붙인다.
- 완료했거나 PR이 열린 작업이면 해당 이슈 항목 아래에 GitHub PR 링크와 Notion PR 문서 링크를 붙인다.
- 기능이 더 커져서 한 페이지에서 보기 어려워질 때만 세부 페이지 depth를 추가한다.
- 새 PR 문서를 만들면 해당 기능 페이지의 이슈 항목 아래에 연결한다.

사람이 앞으로 볼 문서는 항상 페이지 상단에 배치한다.

AI/Codex 인수인계, 보관성 메모, 세부 구현 흐름은 하단에 배치한다.

## PR 작성 전 체크리스트

1. GitHub Issue 번호를 확인한다.
2. 브랜치 이름이 `feat/#이슈번호-작업-요약` 형식인지 확인한다.
3. Notion의 `PR 작업 문서 템플릿`을 복사해 이번 PR 문서를 만든다.
4. PR 문서에 다음 내용을 채운다.
   - GitHub Issue
   - Branch
   - Pull Request
   - 이 PR로 배울 핵심 개념
   - 브라우저/클라이언트 관점의 동작 흐름
   - 서버/Spring 관점의 동작 흐름
   - 이번 코드에 적용된 방식
   - 보안상 주의할 점과 대안
   - 테스트 결과
   - 공식 문서
   - 블로그 / 아티클
   - 리뷰 반영 기록
   - AI 인수인계 메모
5. PR 본문에 Notion 문서 링크를 추가한다.

## 리뷰 반영 시 작성 기준

PR 리뷰나 Codex Review를 반영했다면 Notion PR 문서에도 반드시 남긴다.

리뷰 반영 섹션에는 다음 내용을 포함한다.

- 리뷰 내용 요약
- 왜 문제가 되는지
- 어떤 코드 흐름에서 문제가 발생하는지
- 어떻게 수정했는지
- 관련 커밋
- 수정 후 테스트 결과
- 이번 리뷰에서 배운 점

리뷰 반영 후에는 관련 학습 내용도 함께 최신화한다.

- 최종 테스트 결과
- 리뷰가 나온 근본 원인
- 수정 전후의 요청/응답 흐름 차이
- 같은 실수를 피하기 위한 확인 포인트

단순히 "리뷰 반영 완료"라고만 쓰지 않는다. 나중에 코드를 보는 사람이 같은 실수를 반복하지 않도록, 리뷰가 나온 이유와 수정 원리를 설명한다.

## PR 본문 참고 형식

```md
## #️⃣ 연관된 이슈

resolves: #이슈번호

## 📝 작업 내용

- 

## 테스트

- [ ] `./gradlew test`

## 참고 문서

- Notion: 
```

## 자료 정리 기준

- 공식 문서를 우선 링크하되, 링크만 나열하지 않는다.
- 공식 문서마다 이번 작업에서 참고한 개념이 무엇인지, 그 개념이 어떤 역할을 하는지, 코드에서 어디에 적용했는지 짧게 설명한다.
- 블로그는 공식 문서만으로 이해가 부족한 내부 동작이나 작성 원리를 보완할 때 추가한다.
- 블로그 / 아티클은 가능하면 한국어로 된 자료를 우선 찾는다.
- 한국어 자료는 단순 사용법보다 이번 작업에서 사용한 개념의 내부 동작, 작성 원리, 주의점을 잘 설명하는 글을 고른다.
- 적절한 한국어 자료가 없거나 최신성이 떨어지면 공식 문서나 신뢰할 수 있는 영어 자료를 사용하고, 왜 그 자료를 골랐는지 짧게 남긴다.
- 코드 구현과 직접 관련 없는 자료는 넣지 않는다.
- 나중에 같은 결정을 반복하지 않도록 "왜 이 방식을 골랐는지"를 짧게 남긴다.

## 학습형 문서 작성 기준

핵심 개념은 사용자가 별도 검색 없이 읽고 이해할 수 있는 수준으로 작성한다.

문체는 긴 문장형보다 개조식을 우선한다.

- 한 문단은 최대 2~3줄로 제한한다.
- 설명이 길어지면 bullet로 쪼갠다.
- 흐름 설명은 numbered list를 사용한다.
- bullet은 가능하면 한 줄, 길어도 두 줄 안에 끝낸다.
- 개념 설명은 정의에서 멈추지 말고 이번 PR 코드에서 어떻게 쓰였는지까지 연결한다.

토큰, 보안, Spring 내부 동작처럼 학습 비용이 있는 PR 문서를 작성할 때는 가능하면 서브에이전트를 나누어 활용한다.

- 조사 담당: 공식 문서, 신뢰할 수 있는 블로그, 보안 참고 자료에서 핵심 개념과 출처를 정리한다.
- 문서화 담당: PR 하나에서 배울 목차와 독자의 질문 흐름을 설계한다.
- 메인 작업자: 조사 결과와 실제 코드 흐름을 합쳐 최종 Notion 문서를 작성한다.

각 개념은 가능하면 다음 흐름으로 쓴다.

- 이 개념이 왜 필요한가
- 브라우저나 클라이언트에서는 어떤 일이 일어나는가
- 서버에서는 어떤 검증과 상태 변경이 일어나는가
- 핵심 외부 도구나 프레임워크가 어떤 역할을 맡는가
- 이번 PR의 코드에서는 어느 책임으로 나누어 구현했는가
- 핵심 구현부가 실제 코드 몇 줄로 어떻게 표현되었는가
- 이 방식을 선택했을 때 남는 보안/운영 주의점은 무엇인가
- 다른 선택지는 무엇이고 왜 이번에는 선택하지 않았는가

예를 들어 RTR을 다룬다면 "Refresh Token Rotation이다"에서 끝내지 않는다. access token이 만료된 뒤 브라우저가 refresh cookie를 어떻게 보내고, 서버가 기존 refresh token 식별자를 어떻게 폐기하며, Redis Lua script가 왜 필요한지까지 이어서 설명한다.

Spring Security, JPA, Redis, Validation, Docker처럼 구현의 핵심이 되는 외부 도구를 사용했다면 별도 섹션이나 단락으로 설명한다.

- 이 도구가 이번 PR에서 맡은 책임
- 도구가 내부적으로 요청이나 데이터를 처리하는 흐름
- 이번 코드가 도구의 어느 확장 지점이나 설정을 사용했는지
- 해당 도구를 썼기 때문에 생기는 주의점

예를 들어 Spring Security를 다룬다면 SecurityFilterChain, SecurityContext, 커스텀 필터, permitAll과 필터 실행의 차이를 함께 설명한다.

학습에 도움이 되는 핵심 구현부는 짧은 코드 스니펫으로 포함한다.

- 한 스니펫은 보통 5~15줄 정도로 제한한다.
- 전체 메서드를 붙이기보다 개념이 드러나는 핵심 라인만 고른다.
- 스니펫 아래에는 "이 코드가 어떤 개념을 구현한 것인지"를 짧게 설명한다.
- 단순 DTO, getter, 반복적인 설정 코드는 제외한다.

## 문서 작성 형식

- 제목과 섹션 헤더에는 인라인 코드 형식을 쓰지 않는다.
- Notion에서 macOS Command + E로 적용되는 인라인 코드 래핑은 중요한 키워드에만 제한적으로 사용한다.
- 핵심 개념, 주요 클래스명, 중요한 에러코드, 설정 키처럼 다시 눈에 들어와야 하는 단어에는 사용할 수 있다.
- 단순 파일명, 반복되는 클래스명, 일반 설명 문장에는 남발하지 않는다.
- 명령어, 설정 예시, 짧은 코드 조각처럼 고정폭 표시가 실제로 이해를 돕는 경우에는 코드 블록이나 인라인 코드를 사용한다.

## 핵심 개념 작성 기준

핵심 개념은 단순 키워드 목록으로 쓰지 않는다. 작업자가 나중에 코드를 봤을 때 내부 동작과 작성 원리를 이해할 수 있을 정도로 적는다.

각 개념은 가능하면 다음 내용을 포함한다.

- 문제 상황
- 이 개념이 필요한 이유
- Spring / Java 내부 동작 흐름
- 이 프로젝트에서 적용한 방식
- 다른 선택지도 있었는지
- 주의할 점

예를 들어 Spring 예외 처리 작업이라면 `@RestControllerAdvice`를 썼다는 사실만 적지 않는다. 기본 `/error` 흐름, `HandlerExceptionResolver`, `@ExceptionHandler`가 어떤 순서로 동작하는지까지 적는다.

## AI 인수인계 메모

사람이 반드시 읽어야 하는 섹션은 아니다.

다음 AI/Codex가 같은 맥락을 이어받을 때 필요한 파일 범위, 남은 결정, 주의할 충돌 지점을 적는다.
